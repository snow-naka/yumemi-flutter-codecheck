# AI利用記録

AIへの依頼範囲、ユーザーが判断した内容、実施した確認と未実施の確認を区別して記録する。以降の作業はPRの「AI利用」欄をもとに追記する。

## 開発方法とAI活用の概要（2026-11-25整理）

本記録は、ゆめみFlutterエンジニアコードチェック課題への自主的な取り組みにおける、AIの利用範囲、開発者の判断、検証の履歴を残すものである。企業による選考結果や、AIを使わずに実装した場合の技術力を示すものではない。

現行の機能・起動方法は[README](../README.md)、技術設計は[architecture.md](architecture.md)、環境構築・ビルド手順は[environment.md](environment.md)を参照する。本書の時系列記録にある「未実装」「未検証」「今後の作業」などの記述は、その記録時点の状態を示す。

### 目的と開発の進め方

Flutter未経験からの学習も兼ねて、AIを利用しながらアプリの構造、状態管理、API通信、テストといった要素を理解し、変更理由や検証結果を追える形で開発することを目的とした。

全体を一度に完成させるのではなく、まずFake Gatewayで検索・一覧・詳細・戻る操作が成立する軽量なスケルトンを作り、その上に各機能をタスクとして分けて積み上げることを意識した。設計の検討、実装、検証、レビュー、修正を必要に応じて繰り返し、GitのコミットとPRで変更を管理した。

ただし、実際の作業の細かさのすべてを最初から意図していたわけではない。開発者は以前からAIと一つずつ機能を積み上げる進め方をしており、その傾向が今回のAIの提案にも反映されたと感じている。学習を兼ねた段階開発には意図があった一方、実際には作業を細かく分けすぎた面もあった。これは開発者の振り返りであり、AI内部の学習の仕組みを確認した結果ではない。

今後同様の開発をする場合には、全体の骨組みと機能単位の区切りを意識しつつ、学習のための確認、実装上必要な検証、進行管理上の区切りを区別し、必要以上に工程を細分化しないことが改善の方向として考えられる。

### 利用したAI・ツールと役割

| ツール | 主な利用範囲 |
| --- | --- |
| ChatGPT（通常チャット） | 仕様・設計の相談、技術選定、コード・テスト案の作成、実行結果の分析、修正案、文書・PR説明の整理 |
| ChatGPT（Work） | 実装やリポジトリの読み取り、比較試作の評価、独立コードレビューなど。作業ごとの実施範囲は時系列記録を参照 |
| Codex | 初期資料の整備、環境構築の調査・検証、初期スケルトンの実装とテスト、許可されたGit操作など |
| Claude | データ構造や全体設計の検討時に、別の技術的視点からレビューする役割 |

利用時期・モデル名・レビュー回数を正確に確認できないものについては補完しない。Claudeの役割は開発者の振り返りに基づく概要であり、個々の変更や指摘を根拠なくClaudeの成果として割り当てない。

AIは調査、設計案、コード、テスト、レビュー、文書作成を支援し、作業によっては実装や検証も実施した。開発者は仕様・採否・作業範囲を判断し、AIの提案を開発環境に反映して実行結果を確認するなど、段階に応じて作業を分担した。AIが提案しただけの検証、AIが実行した検証、開発者が実行した検証を区別する。

### 独立レビューの考え方

一つのAIや会話で設計から実装、評価までを続けると、当初の前提や考え方が固定され、問題が見えにくくなる可能性がある。そのため、レビューは原則として実装担当とは別のAIまたは別の会話・作業枠で行い、技術的な別視点から設計や実装を確認する方針とした。

レビューでは指摘をそのまま修正要求にせず、問題の成立条件、発生可能性、影響、既存の対策・テスト、実装・検証・保守コストを比較する。修正が必要な問題は対応し、影響が限定的なものは既知の制約または改善候補として残す。別枠でのAIレビューは見落としを減らすための手段であり、完全な独立性や不具合のないことを保証するものではない。

## 2026-11-25：文書整理時の設計判断の補足

以下は、現行設計書の作成に際して開発者本人に確認した判断理由である。初期の採用時点の記録を変更するのではなく、完成時点での振り返りとして補足する。

### 検索欄の配置

スマートフォンでの操作を想定した際、画面上部の検索欄では使いづらいケースがあると考えた。開発者自身は下配置を好むが、利用者によって好みが異なるため、上下を選択できる方式とした。中段配置は結果一覧を分断し、見やすさを損ねると判断して選択肢に含めなかった。これらは利用者の操作を想定した設計判断であり、ユーザビリティ調査による比較結果ではない。

### 閲覧済み表示

検索結果には似た名前のリポジトリも多く、同じ詳細を意図せず繰り返し開くことを防ぎたいと考えたため追加した。詳細取得の成功ではなく、詳細画面を開く操作をしたことを閲覧済みとして扱う現行仕様は、[現行設計書](architecture.md)を参照する。

### 詳細取得とPR除外Issue数取得の分離

Core APIのリポジトリ応答で得られる`open_issues_count`にはPRが含まれるため、PRを除いたOpen Issue数を取得するには追加のSearch API要求が必要となる。Search APIの利用回数制限が厳しいことから、詳細取得と切り離して必要な情報を取得する方針とした。

開発者は、PR除外Issue数を詳細情報に付随する情報と捉えており、詳細情報がない状態で先に取得したり、詳細取得と並列に要求したりする効果は小さいと判断した。また、課題のIssue数表示とPRを含む件数の扱いを考慮し、自動取得・手動取得の両方で共通の取得処理を使いやすくすることも意識した。

これは取得機能を分離し、詳細を確認した後にIssue数を取得する理由である。HTTP Gateway内部でCore・Searchを共通キューによって直列化することの採用経緯を別途確認したものではない。共通キューの効果・実装仕様は現行設計書に記載する。
