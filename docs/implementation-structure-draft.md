## 1. この資料で整理すること

アプリを「画面」「状態管理」「データ取得」に分け、それぞれが何を受け取り、何を担当し、何を他の部品に任せるかを示す。最初はFake（仮の取得処理）で一連の操作を動かし、その後に実通信へ差し替える、という方向を引き継ぐ。

参照元は、設計メモ追記版の `README.md`、`riverpod-api-notes.md`、`pull_request_template.md` と、これまでの会話。公式課題の要件と自主的な設計案は区別する。文書の短さ・少なさより、目的・仕様・設計・検証が理解できることを優先する。

### 採用状況と理由

当初READMEとの差分だった追加案を採用し、READMEにも同時反映した。開発方針はREADME、要求仕様は公式課題を優先する。

| 項目 | 採用した方針 | 理由 |
| --- | --- | --- |
| UI | Flutter公式のMaterial Design UI。現SDKでは`material_ui`を維持する | 現在のSDKの公式構成と課題のデザイン要件に合わせる |
| 検索結果 | `SearchPage`で一覧・総件数・不完全性・要求ページを保持 | 件数と結果の完全性を区別する |
| リポジトリ情報 | `RepositoryKey`・`RepositorySummary`・`RepositoryDetail`を分ける。詳細は概要を保持し、継承しない | 識別・検索・詳細の役割を明確にする |
| 詳細取得 | スケルトンでも非同期のFake詳細取得を行う | 取得中・失敗・再試行も実通信前に確認する |
| 失敗の伝達 | 成功はデータ、想定する失敗は`ApiFailure`例外 | Fakeと実通信の契約を統一する |
| 状態管理 | 検索は`sealed class`の4状態と`Notifier<SearchState>`、詳細はリポジトリ別の`FutureProvider`。コード生成なし | 検索の操作と詳細取得を分け、状態の二重管理を避ける |
| 入力・保持 | 検索中も編集可能、再送信不可。詳細から戻ると入力・結果・スクロール位置を保持 | 次の入力を準備でき、一覧の続きを見られる |
| 再取得 | 詳細は開くたびに取得。Issue #3では失敗表示・手動再試行、自動再試行は暫定無効。永続キャッシュなし | 実通信の再試行方針はPhase 2で再検討し、有効期限の設計は増やさない |

## 2. 全体構成

```text
アプリの起動・組み立て
  ProviderScope / Providerの定義
    └─ データ取得窓口へFakeまたは実通信の実装を渡す

検索画面
  ├─ 入力途中の文字を画面内で管理
  ├─ 検索操作 → SearchController
  └─ SearchStateを参照して表示
                         │ 検索依頼
                         ▼
              GitHubRepositoryGateway（取得窓口）
                         ▲
                         │ 詳細取得依頼
詳細画面 → 詳細取得Provider（RepositoryKeyごと）
  └─ 取得中・成功・失敗を参照して表示

取得窓口の実装は差し替える
  ├─ FakeGitHubRepositoryGateway：仮データ・待機・失敗を再現
  └─ RestGitHubRepositoryGateway：HTTP・JSON・APIエラーを処理
```

画面は、取得元がFakeかGitHubかを判断しない。検索制御も同じ窓口へ依頼する。検索の状態と詳細の状態は独立させ、詳細取得の失敗で検索結果を消さない。

ここでいう「取得窓口」は、検索・詳細取得の入出力を決めるインターフェース。さらに同じ役割のRepository・Service・UseCaseを何層も追加することまでは、採用範囲に含めない。

## 3. 部品ごとの責務

部品名は識別のための名前。責務を分けることと、すべてを別ファイル・別クラスにすることは同じではない。

| 部品名 | 担当すること | 担当しないこと |
| --- | --- | --- |
| アプリ起動・Providerの組み立て | `ProviderScope`を配置し、取得窓口の実装を提供する。Fake／実通信の切り替え箇所を集める | 検索結果の加工、HTTPエラーの判定 |
| 検索画面 `SearchScreen` | 入力欄、検索操作、案内・待機・一覧・エラーを表示する。選択項目を詳細へ渡す | HTTP要求、JSON項目の直接参照、API固有の失敗分類 |
| 検索制御 `SearchController` | 送信時の検索語を確定する。空入力・検索中の再送信を受け付けず、取得窓口の結果に応じて検索状態を更新する | Widgetの構築、HTTPステータスやヘッダーの解釈 |
| 検索状態 `SearchState` | 未検索・検索中・成功・失敗と、それぞれに必要な検索語・結果・失敗情報を表す | 通信実行、入力欄の編集中の文字の管理 |
| 詳細画面 `RepositoryDetailScreen` | 選択項目の概要と詳細の取得状態を表示する。戻る・再試行を受け付ける | 検索のやり直し、未取得の件数を0にすること |
| 詳細取得Provider | 識別情報を受けて1件を取得し、取得中・成功・失敗を公開する。詳細だけの再試行を扱う | 検索状態の変更、一覧全件の先回り取得 |
| 取得窓口 `GitHubRepositoryGateway` | 検索・詳細取得の入力、成功結果、失敗の伝え方を定義する | 自身に画面状態や表示文言の切り替え処理を持つこと |
| Fake実装 | 検索・詳細の待機、成功、分類済みの失敗を再現する。検索は0件・不完全な結果も用意する | 実通信、画面への直接の仮データ埋め込み |
| REST実装 | URI・要求設定、HTTP実行、応答検査、アプリ用データへの変換、`ApiFailure`への変換、レート制限の待機判断を担当する | 画面遷移、検索状態の直接更新 |
| アプリ用データ型 | リポジトリ、検索結果、識別情報、失敗情報を部品間で受け渡す | API通信やWidgetへの依存を持たせること |

画像取得はAPI応答のアイコンURLを表示側で利用する。画像だけの失敗は代替アイコンで扱い、検索・詳細データ全体の失敗にはしない。

## 4. データと取得窓口の契約（段階2実装済み）

### 主なデータ

| 型 | 主な内容 | 注意点 |
| --- | --- | --- |
| `RepositoryKey` | `id`、`owner`、`name` | 一覧で選んだ対象を識別し、詳細取得へ渡す |
| `RepositorySummary` | ID・名前・所有者・アイコンURL・言語・Star数・Fork数など | 検索応答から得る情報。正確なフィールド対応はAPIメモを参照 |
| `RepositoryDetail` | 詳細表示に必要な情報と`watcherCount` | `RepositorySummary`と追加情報を保持する。概要を継承しない |
| `SearchPage` | `items`、`totalCount`、`incompleteResults`、要求時の`page`・`perPage` | 取得した一覧の件数と総件数を分ける。ページの未取得と結果の不完全性も分ける |
| `SearchState` | 未検索／検索中／成功／失敗、送信済み検索語、成功結果または失敗情報 | `sealed class`で4状態を表し、成功時は`SearchPage`を持つ |
| `ApiFailure` | 失敗分類、HTTPステータス、再試行可能時刻等、利用者向け説明 | 通信失敗・タイムアウト・レート制限・応答形式不正等を区別する。詳細はAPIメモを参照 |

直前の会話で整理した表示対応も引き継ぐ。APIからアプリ用データへ変換する箇所で、`stargazers_count → starCount`、`subscribers_count → watcherCount`とし、`watchers_count`は使わない。画面には「Star数」「Watcher数」を表示し、未取得を0にしない。項目の根拠・説明はAPIメモ第5節と直前の会話にある。

### 取得窓口

採用した取得窓口の契約を再掲する。データ型・窓口・Fakeは段階2で実装済み。検索状態・Controller・検索/詳細の画面は未実装。ApiFailureのHTTP詳細分類や待機情報はPhase 2で拡張する。実装と再現方法は[Fake Gatewayの検証記録](fake-gateway.md)を参照する。

```dart
abstract interface class GitHubRepositoryGateway {
  Future<SearchPage> searchRepositories(
    String query, {
    int page = 1,
    int perPage = 30,
  });

  Future<RepositoryDetail> getRepository(RepositoryKey key);
}
```

成功は上記のデータを返し、想定する失敗は`ApiFailure`を投げる。Fakeと実通信を同じ契約へそろえる。失敗を空一覧やダミーの詳細情報へ変換せず、プログラムの不具合を一律に通信失敗と呼ばない。

## 5. 状態の持ち主と操作の流れ

### 状態の持ち主

| 情報 | 保持先 | 生存期間・扱い |
| --- | --- | --- |
| 入力途中の文字 | 検索画面の`TextEditingController`等 | 詳細から戻っても維持する。検索画面をスタックに残す |
| 送信済み検索語・検索状態・結果 | `SearchController`／`SearchState` | 詳細への移動で破棄せず、戻るだけでは再検索しない |
| 選択した対象・概要 | 詳細画面への引数 | 識別情報と検索時点の概要を渡す |
| 詳細の取得状態 | リポジトリ別の詳細Provider | `AsyncValue`の取得中・成功・失敗を利用し、画面を離れたら破棄する |
| 再送までの待機情報 | 取得側と`ApiFailure` | 画面だけでなく取得側でも早すぎる再送を防ぐ。具体的な保存場所は実通信実装前に決める |

検索は`Notifier<SearchState>`、詳細は`FutureProvider.autoDispose.family`を使う方針。検索の独自4状態に`AsyncValue`を重ねて二重管理しない。コード生成は使わず、検索は詳細への移動で破棄しない。Riverpod 3.5.0の導入版・互換性と基礎APIは段階1で確認済み。検索・詳細の具体的な実装はこれから行う。

### 検索

```text
入力 → 検索操作 → SearchController
  ├─ 空入力：通信せず、検索状態は維持。画面で入力を案内
  ├─ 検索中：新しい検索を開始しない
  └─ 受付：送信済み検索語を確定し、検索中へ
              ↓ searchRepositories()
              ├─ 成功：SearchPageを持つ成功状態へ
              └─ 失敗：ApiFailureを持つ失敗状態へ
```

検索ボタンとキーボードの送信時だけ検索し、再検索開始時は旧結果を非表示にする。検索中の入力編集は許可するが、再送信・別検索・利用者向けキャンセルは設けない。入力途中の文字と送信済み検索語を分け、表示にも送信済み検索語を添える。検索失敗後の再試行は失敗時の送信語を使う。正常0件は成功として扱い、不完全な結果なら別途注意を表示する。

### 詳細と戻る操作

```text
一覧で選択 → 識別情報・概要を渡して詳細画面へ
  → 詳細Provider → getRepository()
      ├─ 成功：詳細値を表示
      └─ 失敗：詳細の失敗を表示。再試行も詳細だけ
  → 戻る：元の入力・検索語・検索結果を表示。再検索しない
```

Issue #3では詳細取得の失敗表示と手動再試行を実装し、Riverpodの自動再試行は暫定的に無効にする。Phase 2でエラー種別・回数・間隔・レート制限への対応を含む再試行方針を再検討する。詳細を離れた後の応答はキャンセルまたは無視し、破棄された状態へ反映しない。詳細は開くたびに取得し、初版は永続キャッシュを設けない。取得中・失敗時も名前等の概要を表示し、成功後は詳細応答の情報で表示をそろえる。戻る際は入力・検索語・結果・スクロール位置を保持し、新しい検索では一覧を先頭へ戻す。アプリ終了後の状態復元は初版に含めない。実通信の再取得・再試行もレート制限の待機を守る。

## 7. 実装の区切りと検証案

まず必要な環境・既存コードを確認する。その後、以下の区切りで骨組みを検証する。各区切りが必ず1コミットや1PRという意味ではない。

| 区切り | 作るもの | 主な確認 |
| --- | --- | --- |
| 1. データと取得窓口 | 採用した型、検索・詳細の契約、Fake | 入出力がそろう。結果あり・0件・失敗・待機を操作できる |
| 2. 検索の骨組み | 検索状態・制御・画面 | 空入力は未送信、二重送信防止、4状態の表示、送信語の保持 |
| 3. 詳細と往復 | 詳細取得Provider・画面・戻る操作 | 選択した1件だけ取得。詳細失敗でも検索結果を保持。戻るだけでは検索しない |
| 4. 実通信 | REST実装と応答変換 | 検索・詳細の成功／HTTP失敗／通信失敗／形式不正／レート制限を区別 |

Controller・画面のテストは取得窓口をFakeへ差し替える。Fakeは待機・成功・失敗・検索の0件と不完全結果を指定でき、テストでは完了タイミングも制御する。REST実装のテストではHTTP応答を差し替え、JSON変換とエラー分類を確認する。Fakeのテスト成功を、実通信の確認済みとは扱わない。

Star数とWatcher数は、例えば120と8のように異なる仮の値で表示を確認する。null・0・未取得を区別し、不完全結果、画像取得失敗、画面を離れた後の応答、自動再試行の抑止もAPIメモのテスト観点に沿って確認する。GitHubへの大量アクセスで制限を発生させるテストは行わない。

最小のCIは骨組みのテストが用意できた段階で追加する案。`flutter analyze`・`flutter test`などの実行結果はPRへ残し、未実行は未実行とする。

## 8. 採用済みの範囲と残る確認

骨組みのデータ分割、失敗の伝達、入力可否、Riverpodの役割・生存期間、スクロール保持、詳細の再取得方針は採用済み。理由なく再検討しない。ファイル分割とレイアウトの細部は実装の分量に応じて調整する。

| 決める段階 | 残る確認・判断 |
| --- | --- |
| 依存関係を今後変更する前 | 現在はflutter_riverpod 3.5.0の版・互換性を確認済み。今後の追加・更新前にも確認する |
| 実通信へ進む前 | Issue数の意味と表示ラベル、追加のIssue検索の要否、HTTPライブラリ・タイムアウト、APIバージョン、待機情報の保存場所、再試行方針（エラー種別・回数・間隔・レート制限への対応） |
| 提出範囲の判断時 | ページングの最終対応範囲、必須要件後のオプション項目 |

骨組みは1ページ分を扱い、初回実通信は先頭30件までを出発点とする。提出範囲の確定とは分け、未決定項目に対する過去の推奨値・候補は確定値としない。

着手の指示後は、環境とGitの初期記録・作業ブランチを確認し、現SDKの公式Material構成の確認・Riverpod導入、取得窓口とFake、検索、詳細と往復の順に進める。採用方針を変更する場合は理由と検証結果を記録し、READMEとAPIメモも合わせて更新する。初期アプリの環境構築結果は開発環境の記録に分け、検索・詳細の実装・テストとは区別する。
